# الموافقة على الأخبار غير الرسمية — المهمة 3

التنفيذ: Cloudflare Workers Free مع SQLite Durable Object، دون خادم دائم أو مدفوع. يقرأ العامل `news_queue.json` من `main`، ويرسل عناصر `unofficial` فقط إلى الخاص مع «✅ انشر» و«❌ تجاهل». لا يُرسل الرسمي للمراجعة. بعد موافقة المالك يرسل للقناة بتنسيق المهمة 2، ثم يحدث `news.json` و`published.json` والطابور في commit واحد. التجاهل يحفظ `ignored.json` ويحذف العنصر من الطابور دون نشره. ملفات الحالة غير موجودة قبل أول جمع/قرار؛ غيابها يعني مصفوفات فارغة، أما JSON التالف فيوقف العملية بأمان.

## النشر والإعداد

1. أنشئ Worker في حساب Cloudflare على خطة **Free** مع Durable Objects SQLite. لا تفعّل خطة مدفوعة. يحتاج CLI إلى Node.js 22+ وتسجيل الدخول إلى حسابك؛ نفّذ من جذر المستودع:
   ```sh
   npx wrangler@4.149.0 login
   npx wrangler@4.149.0 deploy --config news-approval/wrangler.jsonc
   ```
2. أضف الأسرار التالية باستخدام `npx wrangler@4.149.0 secret put NAME --config news-approval/wrangler.jsonc` لكل اسم؛ تدخل القيمة في المطالبة الآمنة، لا داخل الأمر أو الملفات:

   | الاسم | الغرض |
   | --- | --- |
   | `TELEGRAM_BOT_TOKEN` | توكن البوت نفسه المستخدم للنشر الرسمي |
   | `TELEGRAM_REVIEW_CHAT_ID` | رقم محادثة المالك الخاصة؛ افتح البوت وأرسل `/start` أولاً |
   | `TELEGRAM_OWNER_ID` | رقم حساب المالك المسموح له وحده بالقرار، وليس اسم المستخدم |
   | `TELEGRAM_CHANNEL_ID` | القناة العامة؛ البوت مشرف وله حق نشر الرسائل |
   | `TELEGRAM_WEBHOOK_SECRET` | سر عشوائي مستقل، 32 حرفاً أو أكثر من A–Z/a–z/0–9/_/- |
   | `APPROVAL_ADMIN_SECRET` | سر عشوائي مستقل لحماية التشغيل اليدوي؛ لا يُشارك إلا مع المالك |
   | `GITHUB_TOKEN` | Fine-grained PAT لهذا المستودع فقط، بصلاحية Contents: Read and write |

   `GITHUB_REPOSITORY` و`GITHUB_BRANCH` مضبوطتان في `wrangler.jsonc`. يحتاج العامل HTTPS إلى `api.github.com` و`api.telegram.org`. لا تعتمد على توكن جلسة Codex لتشغيل Worker مستقل. لا تضف `GITHUB_TOKEN` إلى الواجهة أو سجلات التشغيل.
3. افحص `/healthz` على عنوان العامل المنشور: 200 تعني وجود الإعدادات، ولا تثبت صلاحيات القناة أو GitHub. ضع `APPROVAL_WORKER_URL` (أصل HTTPS للعامل) و`APPROVAL_ADMIN_SECRET` في GitHub **Settings → Secrets and variables → Actions**. افتح **Actions → Review unofficial news → Run workflow → sync**. بعد جمع أخبار جديدة يشغّل سير العمل هذا المسار أيضًا؛ cron العامل كل ساعة احتياطي. كل تشغيل يرسل خبرين كحد أقصى ضمن حدود الخطة المجانية؛ استخدم sync مجددًا لإكمال طابور أكبر. راقب الحصص المجانية، والـ503 ونتائج `failed` أو `attention` ليست نجاحاً؛ افحص status للحالات التي تحتاج تدخلاً.
4. لتسجيل Webhook، جهّز المتغيرات `APPROVAL_WORKER_URL` و`TELEGRAM_BOT_TOKEN` و`TELEGRAM_WEBHOOK_SECRET` في طرفية موثوقة دون طباعتها، ثم:
   ```sh
   APPROVAL_ACTION=set-webhook node news-approval/admin.mjs
   APPROVAL_ACTION=webhook-status node news-approval/admin.mjs
   ```
   **افحص Webhook الحالي قبل استبداله:** Telegram يسمح بعنوان Webhook واحد لكل بوت. إن كان البوت يستخدم مستقبلاً آخر، وجّه callback إلى هذا العامل من المستقبل الحالي أو خصص بوت أخبار مستقل. لا تستبدل مستقبلاً مستخدماً دون اتفاق. الأمر لا يحذف التحديثات المعلقة ولا يعرض التوكن أو نص أخطاء Telegram.

## البيانات والأمان

الطابور مصفوفة عناصر المهمة 1: `type`, `title`, `url`, `source`, `date`, `summary`, `category`؛ الملخص الفارغ مقبول ولا يُختلق بديل. يُحفظ `source_id` و`collected_at` إذا توفرا. معرّف المراجعة أول 32 خانة من SHA-256 للرابط ثم newline ثم العنوان، متوافق مع بصمة المجمّع؛ لا يُعتمد معرّف يرسله الزائر. Archive يحتفظ بمعرّف المراجعة والطابع الزمني ومعرّف رسالة القناة. لا يُعرض `news_queue.json` أو `ignored.json` عبر خادم الموقع؛ الواجهة تقرأ `news.json` فقط.

يحمي Webhook رأس `X-Telegram-Bot-Api-Secret-Token`، ويتحقق من حساب المالك والخاص ومعرّف رسالة المراجعة. الإدارة محمية بـBearer منفصل. تُسلسل القرارات داخل Durable Object وتُحفظ قبل الإرسال؛ أول قرار نهائي يمنع النقر المتكرر أو القرار المخالف. تعديل GitHub لا يستخدم force، ويعيد القراءة والمحاولة عند تقدم الفرع لحماية تحديثات المجمّع والناشر. قد يفشل push لسير عمل آخر إذا تقدّم الفرع أثناء عمله؛ أعد تشغيل سير العمل الفاشل بدلاً من force push.

إذا رفض Telegram الرسالة صراحةً، يمكن إعادة المحاولة. إذا انقطع الاتصال أو توقفت العملية أثناء الإرسال، لا يُعاد الإرسال آليًا لأن الرسالة قد وصلت. الحالات `sending` و`delivery_uncertain` و`review_sending` و`review_uncertain` تحتاج فحص المالك. فشل GitHub بعد نجاح القناة يحتفظ بـ`published_pending_sync` ويعيد حفظ الملفات دون إرسال ثانٍ عبر alarm بعد دقيقة، ثم خمس دقائق عند الفشل. تُستأنف حالة واحدة في كل alarm لتجنب تجاوز حصص الطلبات؛ sync يدوي يستأنفها أيضًا. تغيير/حذف تخزين Durable Object يفقد ضمان منع التكرار؛ لا تغيّر اسم الربط/الكائن أو تمسح التخزين أثناء التشغيل.

## البديل اليدوي الإجباري عند تعطل Webhook

لا تحتاج هذه الطريقة Webhook فعالاً؛ تحتاج Worker وGitHub والاعتمادات نفسها:

1. اقرأ العنوان والملخص والمصدر والرابط في الخاص وتحقق من الخبر بنفسك. انسخ **معرّف المراجعة** من آخر الرسالة. إذا لم تصل الرسالة استخدم **Run workflow → status** لرؤية المعرّفات والحالات، ثم راجع العنصر المقابل في الطابور؛ إذا لم يقرأ العامل الطابور بعد، شغّل sync أولاً.
2. الأسهل: **Actions → Review unofficial news → Run workflow**، اختر `publish` أو `ignore` وأدخل `item_id`، واترك `channel_message_id` فارغًا. هذا قرار المالك اليدوي؛ لا ترسل الخبر بنفسك في هذه الحالة، فالزر اليدوي ينشر بالقناة والموقع.
3. إذا فضّلت **إعادة إرسال الخبر المعتمد يدويًا**، انسخ نصه للقناة بتنسيق المهمة 2 مع المصدر والتاريخ والرابط (بدون أزرار أو معرّف المراجعة)، مرة واحدة فقط. انسخ رقم الرسالة الفعلي من رابط منشور القناة؛ شغّل الإجراء `publish` بالمعرّف نفسه و`channel_message_id` الحقيقي. يسجل العامل الإرسال الموجود ويحدّث الموقع والطابور والأرشيف **دون إرسال جديد**. لا تدخل رقمًا تخمينيًا. إذا كانت الحالة uncertain، افحص القناة أولًا: استخدم رقم الرسالة الموجودة؛ إن لم توجد بعد التأكد، أرسلها مرة واحدة وأدخل رقمها.
4. شغّل `status` وتحقق من `published` أو `ignored`، وراجع ملفات المستودع ثم الموقع. إذا فشل GitHub، لا تُعد الإرسال للقناة؛ أصلح الوصول وشغّل sync. قرار التجاهل النهائي لا يمكن تحويله للنشر.

لا يعني فقد Worker بالكامل أن النقل للقناة وحده يحدّث الموقع: أصلح وصول العامل أولاً، وأبقِ الخبر في الطابور؛ لا تعتبر العملية مكتملة بصمت.

## التحقق والحدود

```sh
node --test news-approval/tests/*.test.mjs scripts/tests/*.test.mjs
npm test
npx wrangler@4.149.0 deploy --dry-run --config news-approval/wrangler.jsonc
```

تختبر المحاكاة وصول الخاص وأزراره، موافقة المالك والنشر والأرشيف، التجاهل النهائي، الانتحال، تكرار callbacks، القرارات المتزامنة، تعطل GitHub، النتائج غير المؤكدة، النقل اليدوي، والتحديث المتزامن للفرع. عينات الاختبار معزولة؛ `news.json` يبقى فارغاً حتى خبر حقيقي منشور. `sources.yaml` ما زال معلقاً وفارغاً؛ هذا التنفيذ لا يعتمد مصادر غير معتمدة ولا يكمل تدقيق المهمة 1.

الشريط في `index.html` يقرأ `news.json`، ينسب المصدر، يخفي نفسه عند الفراغ ويستخدم المصفوفة المحلية الفارغة عند فشل الجلب (لا توجد مصفوفة أخبار مضمنة في النسخة الأصلية). النص يُضاف بـtextContent والروابط HTTP(S) فقط؛ لا إيموجي أو أزرار جديدة في واجهة الموقع. يدعم RTL وإيقاف الحركة عند التركيز/المرور وتفضيل تقليل الحركة.

النشر إلى حساب Cloudflare وتسجيل Webhook وتجربة Telegram الحقيقية لم تُنفّذ دون الاعتمادات. معيار القبول الحي يحتاج خبراً حقيقياً معتمداً من المالك في الخاص والقناة، ثم فحص الموقع والتجاهل؛ نجاح المحاكاة ليس تأكيداً للإرسال الفعلي.
